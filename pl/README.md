# 損益計算書 自動転記システム（21期テスト版）

Dropboxの請求書PDF・freeeカードCSV・給与集計スプシから、店舗別の損益計算書
`損益計算書 21期（2025.9-2026.8）テスト版` を組み立てるスクリプト一式。

最終更新: 2026-08-20（v20 相当）

---

## 大原則（変えないこと）

- **既存の10個のPLシートには一切書き込まない。** 21期の記録として保管する。
  このスクリプトが触るのは新規に作る `.xlsx` だけ。
- **単位は税抜。円未満切り捨て**（`Decimal` + `ROUND_FLOOR`。floatだと1円ずれる）。
- **判定できなかったものは必ず保留リストへ出す。推測で埋めない。**
- **転記前に一覧を利用者に見せて確認を取る。**
- **カード明細は費目別に仕訳して入れる。一括行には入れない。**
  （利用者指示 2026-08-21）くわしくは下の「カード明細のルール」。

## カード明細のルール（2026-08-21 追加）

**カード明細を読んだ月は、明細1行ずつを費目へ仕訳して入れる。カード会社ごとの
一括行（本部の「JCBカード」「三井住友カード」）には入れない。**

きっかけは二重計上を1件出したこと。7月のJCBは `cards.py` が8費目へ割って
いたのに、既存21期PLの一括額624,249円も `exist_fill.py` が写してしまい、
同じ支払いを2回数えていた（cards.py の税込合計が既存PLの一括額と1円まで
一致したので、同じ明細であることが確定した）。

### 決めごと

| 明細の有無 | 入れ方 |
|---|---|
| **ある月** | `cards.py` が費目別に割る。**一括行は空のまま** |
| **無い月** | 既存21期PLの一括額を暫定で一括行に置く。保留リストに「明細待ち」として出す |

同じ月に両方入ることは絶対に無いようにする。`exist_fill.check(wb)` が
書き込みのあとに検算していて、両方あれば AssertionError で止まる。
`exist_fill.split_by_cards()` が「明細を割った (タブ, 一括行, 月)」を
`cards.py` から自動で作るので、明細を1枚足せばその月は自動で切り替わる。

### いまの状態（21期）

明細があるのは **JCB 7月ぶん1枚だけ**（`202608meisai.csv`）。
三井住友の `202609.csv` は8月ぶんで、21期の9〜7月には効かない。
残り19セル（JCB 9〜6月の10か月＋三井住友 9〜5月の9か月）は一括のままで、
保留リストに出している。

明細を `※請求書※/freeeカード明細/21期/` に置けば費目別に割り直される。
ファイル名は JCB が `YYYYMMmeisai.csv`、三井住友が `YYYYMM.csv`。
**年月は支払月**で、PL列はその1か月前（`cards.py` の FILES に足す）。

※ `statement-YYYY-MM.csv` は freeeカードの明細で別系統（`engine.py` が処理）。
  同じフォルダに入っているが混同しないこと。

## 8月分の受け入れ（2026-08-21 追加）

21期は 2025年9月〜2026年8月。ほかは9〜7月の11か月で組んであり、**8月だけが残っている**。
利用者方針「8月分は全部、CSVかPDFで入れていくのでそれ見て反映していきましょう」。

資料が1つ届くたびにこれを流し、必要なら下の表のとおり1行足す。

| 元データ | 置き場所 / ファイル名 | 8月に要るもの | 対応 |

| PayPay銀行 | `bank/NBG_2026.csv` | 8月の行 | **自動** |

| JCB | `cards/202609meisai.csv` | 9月支払＝8月列 | `cards.py` の `FILES` に1行 |
| 三井住友 | `cards/202609.csv` | 9月支払＝8月列 | **対応済み** |
| 陸事総合 | `rikuji_pdf/202608.pdf` | 利用月＝8月 | `rikuji.py` の `PDF_DATA` に1行 |
| ENEOS | `eneos/ENEOS_8月.csv` | 10月引落＝8月利用 | `eneos.py` に1行 |

### 気をつけること

- **定額（`fixed_costs.py`）を8月へ伸ばすときは、必ず銀行明細で裏を取ってから。**
  毎月同額だからといって先に入れると推測で埋めることになる。
- **按分（`store_bank.py` の `FLAT`）はその口座の明細がある月に限る。**
  2026-08-21 時点で 202608 が届いているのは横丁の 3543920 だけ。
  口座ごとに見るようにしてあるので、CSVを置けばその店だけ自動で8月が出る。
- 2608月フォルダのファイルは、置かれた店舗フォルダと計上先のタブが
  食い違うことがある（ピカピカは本部フォルダだが業務課の行）。
  9〜7月でどの行に入れてきたかを見てから決める。


### Driveへの反映

サービスアカウントを設定すれば `python3 push.py 21期` で直接反映できる（手順は
push.py の冒頭）。この環境から sheets.googleapis.com へ到達できることは確認済み
（未認証で403＝Google本体に届いている、server: ESF）。

**2026-08-20 疎通確認済み。** 21期・22期とも反映に成功し、Drive側のサイズが
ローカルと完全一致した。つまずいたのは Drive API の有効化だけ
（403 accessNotConfigured）。Sheets API は使わないので不要。

**鍵は Dropbox の `/※請求書※/sa-key.json.json` に置き、毎セッション取り直す。**
Dropboxの `download_link` で一時URLを発行して `curl` でディスクに落とせば、
鍵の中身が会話ログを通らない。以下は使わない:
- クラウド環境変数 — 公式ドキュメントが認証情報の格納を明確に禁じている
- Driveの `download_file_content` — 中身をアシスタントに返すため会話に残る

なお、セルを書けるGoogle Sheets用MCPコネクタはレジストリに存在しない
（2026-08-20時点で確認）。サービスアカウント以外の経路はない。

設定していない場合は**手動アップロード**になる。MCPのDriveツールでは代替できない:
- `update_file` はタイトルと親フォルダしか変えられず、セルは書けない
- `create_file` はbase64をインラインで渡す方式で、100KB前後のxlsxは
  アシスタントの1応答の出力上限を超えるため通せない
（push.py はPythonがディスクから読んで送るので、この制約を受けない）

対象ファイル（.xlsxのままDriveに置いてある。ネイティブSheetsに変換すると
IDが変わり push.py が動かなくなるので、変換しないこと）:
- 21期テスト版 `1i7R-v75cigfHjTBCVJ2dzBWOJxAf2Iww` →「2025損益計算書」フォルダ
- 22期        `1DGjxwNznNyXbRu1ovgMtca5zSKQyN0er` →「22期損益計算書」フォルダ

## 毎月の運用（毎月10日）

利用者が毎月10日にDropboxへファイルを入れる。その日の朝9時（JST）に
リマインドのRoutineが飛ぶ。

    Routine: 損益計算書 月次転記リマインド（毎月10日）
    trigger_id: trig_01UaK3bXCZ98XsQkUiokZhG9
    cron: 0 0 10 * *（UTC。= 毎月10日 09:00 JST）
    通知: プッシュ＋メール

★このRoutineは「思い出させる」だけ。取り込みはしない。
  Routineが起動するセッションにはコネクタ（Dropbox・Googleドライブ）が付かないため。
  この環境の組織設定では create_trigger に connectors を渡せない
  （"the connectors parameter is not available for this organization"）。
  自動で取り込みまでやらせたいなら、claude.ai の Routines 画面から
  コネクタ付きで作り直すこと。

取り込みは、ファイルを入れ終わったあとに Claude Code のセッションで
「月次やって」と言う。手順は下の「使い方」のとおり。

## 店舗売上は Airレジの集計CSV から（2026-09-01 追加）

利用者が Dropbox `※請求書※/会計明細/` に Airレジの集計CSVを置くようになった。
**店舗売上の正はこのCSV**。既存の各店PLスプシからの転記はもう使わない。

### 置き方

| 期 | 置き場所 | 中身 |
|---|---|---|
| **21期** | `会計明細/21期/<店舗>_YYYYMM-YYYYMM.csv` （期の直下） | 1行=1か月・12行。遡って埋めるため年間で1本 |
| **22期以降** | `会計明細/22期/<YYMM月>/<店舗>_YYYYMMDD-YYYYMMDD.csv` | 1行=1日。月ごと |

`airegi.py` がどちらも読む（1列目 `集計期間` の先頭6桁で年月に丸める）。
**文字コードは cp932。** utf-8 で開くと落ちる。

    python3 airegi.py          # 取り込み済みCSVと sales.py を突き合わせる
    python3 airegi.py --emit   # sales.py に貼る形で出す

CSVは `pl/airegi/` に落として使う（`bank/` `cards/` と同じ扱い）。

### 消費税の列はCSVに無い。逆算で入れる

CSVにあるのは 売上 と税率別内訳（`売上（10%標準）` `売上（8%軽減）`）だけで、
**消費税額の列が無い**。逆算はできるが、既存PLの値とはぴったり合わない。

りゅうちゃんの21期9月〜7月で比べると、逆算のほうが毎月 129〜235円 多い。
その差は会計数にきれいに比例する（**差 ÷ 会計数 ≒ 0.47円**、11か月で計2,138円）。
POSが会計1件ごとに切り捨てているため。「既存PLの消費税＝かめや合計精算書の
POS売上明細表の日別消費税の合計」（下の確定済み判断）とも整合する。

**決めごと（利用者指示 2026-09-01）**

| 状況 | どうするか |
|---|---|
| その月の既存PL値がある | **既存PL値を残す**（POS精算書由来なので逆算より正しい） |
| 既存PL値が無い | **逆算を入れる**。空欄だと売上合計(1)が税込のぶん過大になるため |

逆算は `airegi.py` の `read_csv()` が出す。**月合計を税率ごとにまとめてから割る**
（日ごとに割ると誤差が積む）。`airegi.py` の表示と `--emit` は逆算行に `※逆算` を付ける。
既存値があって逆算とずれている月は「（既存PL優先・逆算との差）」と出して、
要確認としては数えない。

より正確にしたければ、その月のPOS精算書（日別消費税が載っているもの）をもらって
差し替える。

### さわら十三里屋は21期だけ税抜

既存の十三里屋PLは見出しが「単位：千円（税抜）」で、売上行が1本（消費税行が無い）。
他店は「売上（税込）＋消費税」。AirレジCSVは税込なので、**21期の十三里屋の行だけは
税抜に逆算してから入れる**（`airegi.key_for()` がこの1か所だけ分岐している）。

**22期からは他店と同じ「売上（税込）＋消費税」に揃える**（利用者指示 2026-09-01）。
`sales.SALES_ROWS_22` と `sales.rows_for(tab, period)` で期ごとに切り替えている。
21期の既存シートは記録として触らない。

### 21期の突き合わせ結果（2026-09-01・Airレジ5店ぶん全部）

年間CSVが5店そろったので21期の全月を照合した。**直すところは無かった。**

| 店 | 行 | 結果 |
|---|---|---|
| りゅうちゃん | 売上 | 12か月すべて1円まで一致 |
| もも焼きJAPAN | 売上（税込） | 12か月すべて1円まで一致 |
| 韓国酒場ハナ | 売上（税込） | 12か月すべて1円まで一致 |
| タコとハイボール | 売上（税込） | 12か月すべて1円まで一致 |
| さわら十三里屋 | 売上（税抜） | 9月〜7月は逆算が257〜1,212円**少ない**。既存PLを残す |

十三里屋のずれの向きが消費税行と逆（逆算のほうが少ない）なのは、
`税抜 = 税込 − 消費税` で逆算消費税が多めに出るから。理屈が合っている。

1割ずれるはずが、実際は0.05%以下しか違わない）。

そのまま。**8月に入れた逆算も同じぶんだけ多め**（十三里屋の8月は会計数1268なので
税抜が600円ほど少なめに出ているはず）。精算書が手に入れば差し替える。

## ハマりどころ（再発防止メモ）

### 1. 利用店名は「`<店名> <カード名>`」の連結
`焼きたて屋コメリパワー鹿島店` のようにカード名が末尾に付く。そのまま
マスタ照合すると「コメリ」「横丁」などに誤ヒットする。`engine.py` の
`merchant_only()` でカード名部分を削ってから照合すること。これで保留20→7件になった。

### 2. 端数は必ず `Decimal`
`math.floor(30800/1.1)` は 27,999 になるが正解は 28,000。370行中27行がずれた。

### 3. 税率のメモは「内容」列ではなく「領収書メモ」列
「内容」列は376行すべて空。

### 4. 請求書フォルダの月 → PL列は「同じ月」
`2606月` フォルダ → **6月列**。既存スプシの年計と月次の合計を突き合わせて確認済み
（りゅうちゃん ガス料金 年計221,039 = 月次11件の合計）。5月列ではない。

### 5. 2606月だけ `確認済/` のサブ階層がある
2607月以降はない。

### 6. 本部の請求書の置き場所が月によって違う
2606月は本部フォルダがなく「業務」フォルダに混ざっていた（室田石油・スギヤマ・高塚誠・
帝国データバンク・ロータリークラブなど）。2607月から「本部」フォルダが新設された。
業務課のスプシに行がない請求書が出たら、まず本部を疑うこと。

### 9. フォルダは後から増える。必ず差分を取ること
2607月は初回に読んだ時点で23ファイルだったが、3日後には60ファイルになっていた。
「もう読んだ月」でも、処理済みファイル一覧と `list_folder` の結果を突き合わせて

（鹿島食品→りゅうちゃん宛の請求書が焼きたて屋フォルダに置かれていた）。

### 7. 同じ取引先で契約が複数ある
USEN×2、NTTファイナンス×2、電気料金×2（東京電力EP 看板／地域創生HD）。
1件にまとめないこと。

- 2025年9月〜2026年3月の人件費は入力しない
- 既存スプシに税込のまま入っている行があるが、新シートは税抜で統一する

  「ロータリークラブ」行（売上原価・91,000）は動かさない
- **2か月分まとめて請求されたものは月ぶんけする**。エクセレントリーダーズの
  EL会費は@10,000×2件で2026.7,8月分なので、7月と8月に1万円ずつ入れた
  （フォルダは2607月だが中身が2か月分）
- **定額の自動引落・自動振込は既存スプシから入れる**（請求書が来ないため）。
  全タブが対象（`fixed_costs.py`）。11か月とも同額の行だけ。
  1か月でも違えば入れない（都度請求の可能性）。
  すでに請求書から入っている月は飛ばし、そのとき「請求書の額＝定額」を
  assert する。重なりは事故ではなく検算材料として使う。
  消費税は「÷1.1が割り切れる行だけ税抜に直す」（フォーゲル55,000→50,000、
  五十嵐商会2,530→2,300）。残りは税抜か税込か数字から判断できないので触らない。
  対象は9月〜7月の11か月。8月は月が締まってから
- **マイナスは赤字表示**。書式は `#,##0;[Red]-#,##0`（比率は `0.0%;[Red]-0.0%`）。
  build2.NUMFMT / PCTFMT に定義してあるので、新しくセルを書くときはこれを使う
- 藤原ストアーの「空瓶・空樽代金など」は**仕入から差し引く**（6月 6,736−440=6,296／7月 9,696−1,230=8,466）
- ビアガーデンの飲食代4社（ガキゲン・居酒屋ドリーム・鉄板焼次郎・ツマギアンズ）は
  神栖横丁に**取引先名で行を新設**。消費税の記載がない2社は10%で逆算する
- 本部 室田石油の7月は請求書どおり **6,922**。既存スプシの1,384は既存側の入力誤り
- **JCB・三井住友は支払日ベース**（ファイル名の年月 −1ヶ月 = PL列）。
  JCBは15日締め翌月10日払いで1枚が3ヶ月分の利用日にまたがるため、利用日ベースだと
  毎月2枚必要になり月次が1ヶ月遅れる。明細ログに利用日を残してあるので後から変更可能
- **カード明細に税額の記載がないため10%で逆算**（軽減8%の可能性がある少額品も10%扱い）
- **焼きたて屋の売上集計表は22期から**（A-2）。元ファイルが2026.03以降しかなく、
  21期に入れると消費税の計算方法が期の途中で変わるため。方法A＝税率別の税込から
  内税を抽出（10%は10/110、8%は8/108、円未満切り捨て）。
  ★ただし2026-08-20に既存PLの消費税の正体が判明した：**かめや合計精算書のPOS売上
  明細表の日別消費税の合計**をそのまま写したもの。日別合計のほうが実態に近いので、
  22期は方法Aではなく精算書の値を使う（`kameya.py` 参照）
- **出前館は 売上①・手数料⑥税抜・返金⑦ の3つを21期に入れる**。消費税だけは既存の
  計算方法（①×8%）のまま触らず、22期から内税抽出（8/108）に揃える。
  ★以前このREADMEに「手数料は21期に計上漏れ」と書いたが**誤り**。既存PLスプシを
  実際に読んだところ 支払手数料（出前館）140,843／同（出前館返金）▲20,890 が
  すでに全月入っており、しかも本システムの計算値と11か月とも1円まで一致した。
  計上漏れではなく検算材料。`demaekan.EXIST_21_FEE` / `EXIST_21_REFUND` で assert している
- **出前館のお戻し金額⑦は費用のマイナス**（雑収入ではない）。既存PLがその扱い。
  `支払手数料（出前館返金）` にマイナスで入れる
